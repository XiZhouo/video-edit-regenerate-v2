1 · Build:mod 级跨 skill 共享域层受管模式 Build

What

P0 建了独立源仓 ZE-video-timeline-domain,用 sync_domain.py 把 src/ze_video_domain/ 分发进三个消费 skill 的 02-mod/05-code/_domain/,并在投影里写版本锁 _DOMAIN_LOCK.json、 在源仓登记消费方 domain_lock.json,提供 --verify 判 OK/BEHIND/DRIFT/MISSING。

Why

build-v3 现有受管层全是 framework → mod 的纵向层:01-core / sdk / 04-ops / 05-i18n / 03-css-rules,由 skill_sync.py 按 _locks/*.lock.json 的 interface_version + checksum 判 same / compat_bump / incompat。

而视频四件套需要的是一个 mod 级、跨兄弟 skill 的横向共享域层:①②③ 各自 02-mod/05-code/_domain/ 装同一份引擎(schema / clip_math / ffmpeg_ops / send_compiler / candidate_flow / strategy),避免「第三套 schema 让分裂变三份」。 这是 build-v3 受管层体系里没有的第四种形态。当前我在域仓里自造了一套等价机制(源→投影、版本锁、checksum drift、回流纪律), 但它游离在 build-v3 的 verify_all / managed_drift_check 治理之外。

Where(具体改哪里)

  • ZE-skill-build/scripts/skill_sync.py:新增 _domain 作为可识别的 mod 级受管层类型; 或提供一个 domain_sync 姐妹脚本被 build-v3 收编,统一 lock 语义(ze.video_domain_lock.v1 ↔ ze.interface_lock.v2)。
  • ZE-skill-build/scripts/managed_drift_check.py:把 02-mod/05-code/_domain/ 纳入 drift 检查 ——它虽在 02-mod(作者层,sync 不碰),但对域仓而言是投影,私改必须被咬(检出 DRIFT → 回流)。
  • ZE-skill-build/scripts/verify_all.py:增一个软门 domain-lock-consistency,校验消费 skill 的 _DOMAIN_LOCK.json 与其声明的源仓版本一致(缺源仓时软跳过,像 upstream-only 门那样)。
  • 文档:ZE-skill-build/EXTENSION-RULES.md 加一节「跨 skill 共享域层」,写明受管层必回流上游纪律与 「sync 前必跑消费方 verify_all 防 clobber」硬令(与 ZE-video-timeline-domain/_MANAGED_LAYER.md 对齐)。

How(我如何假设已反哺后开发)

我把域仓当作「build-v3 已经正式支持共享域层」来写:

  • 投影里放 _DOMAIN_LOCK.json(schema ze.video_domain_lock.v1),形态对齐 build-v3 的 _locks/*.lock.json;
  • _MANAGED_LAYER.md 明写三条纪律(必回流 / sync 前跑门禁 / 版本锁登记),即 build-v3 收编后应强制的规则;
  • _domain/ 用相对导入的独立包,可原样搬进任意 skill 的 05-code —— 已实证 from _domain import schema 在 mod-code 路径下正常。

未做(有意):把 _domain 挂进 ②③ 并证明「行为零变化」(既有 e2e 原样过)——规划里这步有人工 schema 评审门, 不在无人值守夜间执行。① 已作为首个消费方接线并验证。

2 · Build:两条隐性字段契约 Build

What

造 ① 的 document_register.py 时,踩到两条 build-v3 字段类型系统的隐性契约,文档/脚手架都没显著提示:

契约现象正确写法
enum 仅限 string 类型字段{"type":"number","enum":[1,2,3]} → framework validator schema is malformed(field_types.py:554,enum ∈ _STRING_KEYWORDS)数值枚举改用 minimum/maximum,或把值改成 string enum
typed string 字段拒 Nonedata 里把可选 string 设成 None → expected string (got None)(field_types.py 对存在的字段严格校验)可选字段省略键而非置 None(本轮加了 _compact() helper)

Why

这两条都是「本可从文档一眼避免」的坑,却要靠 bootstrap 时的运行期报错才发现。config 的 kind 同类: 必须是 bool/float/enum/text 而非直觉的 boolean/number/string(config_schema.py VALID_KINDS)。 对「让任何档位的人讲清业务就能造工具」的 System 目标而言,这类隐性契约应前置到文档与脚手架注释,减少 AI/人反复试错。

Where

  • ZE-skill-build 的字段类型文档(01-core/01-data-structure/04-field-types/ 附近的 README 或 TYPE-REGISTRY.md): 显式列出「enum 仅 string」「typed string 字段省略 ≠ 置 None」「config kind 白名单」三条。
  • 可选增强:放宽 field_types 允许数值 enum(若产品需要数值下拉),但这是行为变更,需谨慎;先补文档成本最低。
  • skill_scaffold.py 生成的 document_register.py 占位注释里加一行提示这三条契约。

How

我按「已知这三条契约」写代码:数值 mode 用 minimum/maximum;可选字段一律经 _compact() 省略 None;config 用 bool/float/enum/text。当前 ① 的 21 个 mod 单测全绿即证明这套写法成立。

附:scaffold 的 recipe-v3 → artifact-variant 签名缺口(Build ↔ Deploy)

现象。scaffold 生成的 deploy.json 是 ze.deploy-recipe.v3(portable delivery_modes: local-full / self-hosted-full),artifact-variant 门因此要求一份已签名的 ZE_ARTIFACT_VARIANT.json (Ed25519 detached signature)。但 scaffold 不生成它,且生成它(release_builder.py)需要: ① 一份 ready(依赖锁定)的 ZE_DEPENDENCIES.json;② 一把必须放在 skill 根之外的签名私钥。 两者都是 Deploy/release 阶段的产物 —— 一个刚 scaffold 出来的 skill无法自行通过 artifact-variant。

本轮处置(已改为可部署)。①②③④ 全部代码质量门已绿。为满足「能部署」,① 的 deploy.json 已从 scaffold 的 recipe-v3 改为 legacy 形态(与现役生产 v3 skill 如 image-prompt-studio-v3 一致: {skill,port,bind_host,start,install,healthcheck_path,rsync_exclude,name}),并移除随之无意义的 ZE_ARTIFACT_BUILD.json。这样 artifact-variant/artifact-build/deployment-profile 全绿、无需签名即可 verify_all 通过并写 ZE_BUILD_EVIDENCE.json。recipe-v3 + Ed25519 签名仍是 更现代的目标态,但它需要组织发布私钥(Deploy 阶段),未在无人值守夜间用临时 dev key 伪造(no-fake-artifacts 硬令)。

反哺建议。要么 scaffold 生成 legacy deploy.json(现役生产 v3 skill 如 image-prompt-studio-v3 正是 legacy 形态、不带 artifact-* 文件、full verify 绿),要么在文档里写明「recipe-v3 新 skill 的 artifact-variant 是 Deploy 签名门,scaffold 阶段预期红,须 Deploy 锁依赖+签名后转绿」,避免把「未签名」误读成「构建缺陷」。

3 · Design:媒体编辑候选原型 Design

What & Why

① 是一个可复用的新原型:时空标注(空间 bbox × 时间区间)→ 确定性编译提示词 → AI 产候选(不覆盖正本)→ 机检红黄绿 → 人采纳/回贴。 这条「候选制 + 机检门 + 判断权保留」的媒体编辑骨架,不止视频,图像/音频编辑同构(S2D 就是它的图像版)。design skill 的 intake 原型库 (ZE-skill-design/references/intake-*.md 的 archetype-library)目前没有这个原型,下一个做类似工具的人得从头推。

Where

  • ZE-skill-design intake archetype 库新增 media-edit-candidate 原型:声明其判断点(该改什么 / 行不行 / 接不接得上)、 机器自动项(编译 / 机检 / 回贴)与人拍板项(采纳 / 重生成),并给出 candidate + verify_report + send_job 的信息对象模板。
  • 把「结果本体决定 UI」在此原型的落法写清:视频结果有家(时间线/画布)→ 落时间线;无家才候选画廊(与既有 result-ontology-decides-ui 纪律一致)。

How

P0/P1 的 candidate/verify_report/send_job 三实体 + candidate_flow(stale 拒采 / 空段自动采纳)已把这个原型的语义内核实现出来, 可直接抽象成 design 的原型模板;本轮按此内核开发,未回填进 design 文档。

4 · Deploy:退役流程正式化 Deploy

What & Why

退役盘点(01-现有视频工具退役盘点.md)结论:四件套整合掉一条 v2 老链,需退役 7 工具(A 旧版重复 2 + B 空壳 1 + C 被取代 4)。 但退役目前只是一份散文 SOP:查下游硬引用 → registry 标 retired(不删,留审计)→ 服务下线 → 归档不物理删 → catalog 刷新。 Deploy 缺一条正式的 Retire 命令流把这几步变成可审计、可回滚、幂等的操作。

Where

  • ZE-skill-deploy 增 Retire.* 命令族:Retire.Preflight(grep 全库硬引用/handoff/端口)→ Retire.Mark (registry status/lifecycle=retired,runtime_status 置停,保留数组条目)→ Retire.Teardown(停端口 + 清 keepalive 复活者,顺序按 deploy-identity-audit-traps 纪律)→ Retire.Archive(移归档区,no-delete)。
  • ZE-skill-system/registry/registry.json 的 work_skill schema 增 lifecycle 枚举(active|retired)与 retired_at / superseded_by,让 catalog 投影能显示「已退役,被 X 取代」而非静默消失。

How

本轮不执行任何退役(no-delete 硬令 + 每步人确认 + C 类绑 P4 验收后才退)。这里只把退役需要 Deploy/System 提供的机制列清, 供正式做退役时先补齐 Deploy 能力,再照 SOP 执行。

5 · System:共享域源仓类目 System

What & Why

ZE-video-timeline-domain 是一种新的制品类型:既不是 work skill(不部署、无 surface),也不是四标准 skill, 而是一个被多个 work skill 消费的共享受管源仓。System 的 registry 三数组(standard/support/work)没有它的位置, 于是它现在对目录与治理是不可见的——没人能从 catalog 发现「有这么一个共享域层、谁在消费它、版本几何」。

Where

  • ZE-skill-system/registry/registry.json 增第四类 shared_sources(或给 support 数组加 kind=shared_domain), 登记 ZE-video-timeline-domain 的版本、消费方列表(镜像 domain_lock.json)、schema 契约 id(ze.video_project.v1)。
  • System Console 目录投影增「共享域层」视图,显示消费方与各自 OK/BEHIND/DRIFT 同步态(数据来自 sync_domain.py --list 与各投影的 lock)。

How

域仓自带 domain_lock.json(schema ze.video_domain_registry.v1)已是这份治理数据的机器真源, System 收编时直接读它即可,无需重造。本轮按「System 已能登记共享源仓」假设,把治理数据落在域仓内。
